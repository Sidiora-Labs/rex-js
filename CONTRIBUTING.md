# Contributing to Rex

Rex is built from a spec, one task at a time, by people and agents following the same contract. The full contract is `spec/workflow.kvx`; [docs/development.md](docs/development.md) explains the workspace, the tests, the gates and the workflow in detail.

## The operating contract

1. **Spec first.** Work comes from the task list in `spec/rex/spec.kvx`. Read `[meta]`, `[decision]`, `[design]` and the acceptance criteria (`[req.*]`) before you change code. A change that has no task needs a task first.
2. **One task at a time.** Claim a task (`cg spec claim-next --agent <name>`, or `cg spec next` and `cg spec start <id>`), and edit only the files in its `touches`. A change needed outside them is a new task, recorded in the qualification log.
3. **Implement, then qualify once.** Write the whole task and its tests first. Then format the touched files, run one typecheck and the task's single `verify_cmd`. You get at most two repair cycles and 30 minutes.
4. **No weakening.** Never relax an assertion, loosen a bound, widen a type, add a silent fallback, skip or delete a test, or disable a check to make something pass. No stubs, mocks or fake implementations. If the code and a check disagree, leave both and record the conflict.
5. **Mark done honestly.** Run `cg spec done <id>` only after `verify_cmd` passes, and never with `--force`.
6. **Commit per task** in the house format: eight lines (`rex-main`, `fm-rex`, date, branch, the SHA of `HEAD` before the commit, the quoted title with its `[spec:...]` tag, a blank line, the `Signed By` line), then a blank line and the `Co-Authored-By` trailer. See [docs/development.md](docs/development.md#commit-message-format).
7. **Record findings, do not chase them.** An unrelated failure, a contradiction between tasks, or a fix that would need a weakened check goes into `spec/rex/qualification.kvx` as one entry of at most six lines with the keys `task`, `file`, `symbol`, `observed`, `assumption` and `severity` (`blocker`, `suspect`, `assumption` or `note`), naming the revision, command, exit code and log path. Do not log the same finding twice.

## Conventions to keep

- One way to declare an action, lay out a page folder, navigate, and expose an affordance. Do not add a second pattern for something Rex already has.
- No Next.js, React Server Components or server actions. Server code is Hono plus oRPC; client code is React.
- Every control Rex emits must be operable by an agent: a `data-rex` address, a sidecar entry, a visible counterpart, and no hover-only or drag-only interaction.

## Generated files

Do not edit `AGENTS.md`, `CLAUDE.md` or the markdown mirrors in `spec/rex/` by hand; they are generated by `cg spec render`. `examples/demo/AGENTS.md` and `examples/demo/.rex/manifest.json` are generated by `rex manifest`.

## Before a release

The release gates `tools/gate-test.sh` and `tools/gate-lint.sh` run the package tests, the typecheck, `rex check` on the demo, the demo's Playwright operability walk, and `cg spec render --check`. They run once per wave on the merged revision, not per task.
