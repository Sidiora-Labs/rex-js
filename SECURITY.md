# Security policy

This policy covers the `@sidioralabs/rex` package, its `rex` CLI, the Vite plugin, the server and client runtimes, and the code generated by `rex new` and `rex make`. The demo in `examples/demo` is covered as far as it shows Rex behaviour; it is not a production application.

## Supported versions

Rex is before 1.0. Security fixes are released for the latest minor version; the previous minor version receives fixes for critical and high severity issues for 90 days after the next minor version is published.

This table applies from the 0.2.0 release; 0.1 was never published to npm.

| Version | Supported |
| --- | --- |
| 0.2.x | Yes |
| 0.1.x | Not published; upgrade with `rex migrate` (see docs/migration.md) |
| Earlier | No |

After 1.0, the latest major version receives all security fixes and the previous major version receives critical and high severity fixes for twelve months after the next major version is published.

## Reporting a vulnerability

**Do not open a public issue, pull request or discussion for a vulnerability.**

Report it privately through GitHub's private vulnerability reporting: open the repository's **Security** tab and choose **Report a vulnerability** (`https://github.com/Sidiora-Labs/rex-js/security/advisories/new`). The report is visible only to the maintainers listed as security contacts in [MAINTAINERS.md](MAINTAINERS.md).

Please include:

- the affected version or commit and the runtime (Node, Bun, Deno or edge) and adapter;
- the component: action router, form route, CSRF or Origin checks, CSP, the client bundle boundary, the audit ledger, the CLI, the Vite plugin, or generated code;
- a minimal reproduction, ideally a small Rex app or a failing test;
- the impact you observed or expect, and any proposed fix.

If you cannot use GitHub, ask in a public issue for a private contact without describing the vulnerability, and a maintainer will reach out.

## What happens next

| Step | Target |
| --- | --- |
| Acknowledge the report | Within 3 business days |
| Confirm or reject the issue and assess severity (CVSS) | Within 10 business days |
| Agree a disclosure date with the reporter | When the issue is confirmed |
| Release a fix for critical and high severity issues | Within 30 days of confirmation |
| Release a fix for medium and low severity issues | Within 90 days of confirmation |
| Publish the advisory | When the fixed version is on npm |

We follow coordinated disclosure. The default embargo is 90 days from the report or until a fix is released, whichever comes first; we may agree a different date with the reporter when a fix needs more time or the issue is being exploited. If we miss a target, we tell the reporter why and when to expect the next update.

Fixes are released as patch versions for every supported line through the normal release process in [GOVERNANCE.md](GOVERNANCE.md), with the waiting periods waived. Each fix gets a GitHub security advisory, with a CVE requested through GitHub, naming the affected and fixed versions and crediting the reporter unless they ask to stay anonymous. The fix is listed in [CHANGELOG.md](CHANGELOG.md).

## Scope

In scope:

- bypassing an action's policy, the confirmation required for irreversible actions, or the flow approval gates;
- cross-site request forgery or Origin check bypass on `/rex/rpc` or `/rex/form/*`;
- script injection through output Rex renders, including the sidecar, the outcome region, the palette and server-rendered pages, or a bypass of the CSP nonce;
- server-only code, action handlers or secrets reaching the client bundle despite the build checks;
- tampering with or forging audit ledger records;
- vulnerabilities in code generated by `rex new` or `rex make` as generated.

Out of scope:

- vulnerabilities in an application's own action handlers, policies or data stores, unless Rex makes them unavoidable;
- vulnerabilities in dependencies with no exploitable path through Rex (report those upstream; we still welcome a note);
- issues that need a compromised development machine or a malicious `rex.config.ts`;
- missing hardening that is documented as the application's responsibility.

## Safe harbour

We will not pursue legal action against anyone who researches and reports a vulnerability in good faith under this policy: who avoids privacy violations, data destruction and service disruption, tests only against their own installations, and gives us reasonable time to fix the issue before disclosure.
